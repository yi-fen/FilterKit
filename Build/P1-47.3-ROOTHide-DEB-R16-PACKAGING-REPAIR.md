# P1-47.3 — RootHide DEB Packaging Repair (R16.1 Reference)

## Scope

This change repairs only the RootHide DEB packaging route. P1-46 App/plugin scanning, Helper runtime, and TrollFools-related discovery work are not modified. No Xcode build was run.

## R16.1 source facts used

The uploaded `FilterKit-Plugin-Operations-Optimized-Next9.6R16.1-ImportFix.zip` contains:

- `Config/DEB/roothide.env`: RootHide package architecture `iphoneos-arm64e`, rootfs payload `Applications/FilterKit.app`, minimum binary slice `arm64`.
- `Config/DEB/control`: RootHide package metadata, including `Depends: firmware (>= 15.0), ellekit`.
- `Config/DEB/postinst`: registration-only `uicache -p /Applications/FilterKit.app` hook.
- `scripts/sign-app-ldid.sh` and `scripts/validate-ldid-signature.sh`: sign nested Mach-O images first, sign the main executable with the configured entitlement plist, then check `LC_CODE_SIGNATURE`, CDHash extraction and exact embedded-entitlement equality.
- `scripts/package-deb.sh`: builds the RootHide rootfs package separately from Rootless.

R16.1 explicitly says that its four private entitlement keys are candidates and that static signature validation does not prove RootHide/amfid acceptance, installability, or launch stability. This release keeps that distinction; it does not claim device verification.

## P1-47.2 defects addressed

1. P1-47.2 wrote `Architecture: iphoneos-arm64`, which is the Rootless package label. RootHide now uses `iphoneos-arm64e` as the DEB metadata architecture.
2. RootHide payload remains rootfs-relative `Applications/FilterKit.app`; no `var/jb/Applications` prefix is emitted.
3. The package now declares the R16.1 RootHide dependencies `firmware (>= 15.0), ellekit`.
4. The app's Mach-O architecture is validated independently. The package metadata label `iphoneos-arm64e` does not force an arm64e-only Mach-O; an `arm64` slice is accepted, matching the R16.1 profile.
5. The previous Apple ad-hoc `codesign --deep` step is no longer used for the RootHide DEB. The staged app is signed with the R16.1 `ldid` flow, including nested Mach-O signing and a post-sign static validation pass.
6. The DEB is extracted after creation and its signatures are validated again, reducing the chance that packaging/copying silently drops or damages signature data.
7. `postinst` is limited to best-effort SpringBoard registration. It does not modify ElleKit configuration, plugin files, or dpkg state.

## Output contract

For a RootHide Release build, the package is:

- Debian package name: `cn.yfen.filterkit`
- Architecture field: `iphoneos-arm64e`
- Payload: `Applications/FilterKit.app`
- App registration path: `/Applications/FilterKit.app`
- Dependencies: `firmware (>= 15.0), ellekit`
- Filename pattern: `cn.yfen.filterkit_<CFBundleVersion>-1_iphoneos-arm64e.deb`

The selected workflow label (`arm64` or `arm64e`) remains a device/build label. Both use the project's supported arm64 iOS app slice; the RootHide DEB metadata remains `iphoneos-arm64e` in either case. This is the R16.1 package-profile distinction.

## Crash-prevention checks added to the package path

- `CFBundleIdentifier`, marketing version, build version and `CFBundleExecutable` are read from the actual app Info.plist.
- Main executable must exist and retain its executable bit.
- `lipo` must confirm an arm64 or arm64e slice.
- Every Mach-O in the app bundle is signed/checked by the R16.1 ldid scripts.
- The main executable's embedded entitlements must exactly match the source plist.
- `LC_CODE_SIGNATURE` and CDHash extraction are checked for each Mach-O.
- The signed app is re-checked after DEB extraction.
- Package metadata, RootHide payload path, postinst syntax and absence of a Rootless `/var/jb` payload are checked.

These are static integrity checks. They cannot prove that RootHide accepts the candidate entitlement set, that the package manager installs it on a particular device, or that SpringBoard can launch it. Device installation, cold launch, and post-reboot launch remain required acceptance tests. If the app still exits immediately, collect the device `.ips`/crash log rather than changing entitlements speculatively.
